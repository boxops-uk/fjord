This page follows one query all the way through.

```sigla
{f = F, at = S} where
  codemarkup.SearchEntry {nameLowercase = _, name = "Crc32", kind = _, symbol = T, file = _, line = _};
  codemarkup.SymbolXRef {target = T, file = F, span = S}
```

## The whole journey

<Journey>{`
# client
you type it
the client holds the served schema (frame H, then h)
the shell compiles it locally. A mistake stops here
QUERY frame on a new stream: [Q][stream][len][the text]
| one socket, many streams
# server
the reader task routes the frame to that stream's own task
hop off the reactor onto the blocking pool
compile: lex, parse, typecheck, flatten, reorder, Plan
ROW_DESCRIPTION frame (T): the head's shape, once
open a snapshot, enumerate 256 rows
encode each row with the transport codec into DATA_ROW frames (D)
suspend to a bytes-only Cursor, drop the snapshot
… and again per chunk, while the previous chunk is being written
PROFILE (p) if asked, then COMPLETE (C) with counts
| the rows come back
# client
decode each row against the descriptor
expand references, if asked: a FETCH round trip per level
render: table, json, jsonl, raw, or a count
`}</Journey>

## 1–2. The client knows the schema

A client connects with a startup frame naming the database, a session mode, and the
predicates it claims. Then it can ask for the schema the database is served with:

<Sequence>{`
→ H  "what can I ask you?" — no payload
← h  the schema this session is served with, as source
`}</Sequence>

A database carries its own schema, frozen at create. With it, a client can compile queries
and show plans locally.

## 3. The client compiles it

The shell compiles every query before sending it, so a mistake is a diagnostic with no
round trip:

```text
error[reject/unknown-predicate]: `src.Nope` is not a predicate in this schema
  ┌─ <input>:1:9
  │
1 │ X where src.Nope X
  │         ^^^^^^^^^^
```

`fjord query` sends the text first and compiles locally only to render the caret if the
server refuses it. Where the two compilers could disagree, the server decides what runs.

Every frame names its stream, so several queries and writes share one socket and a long
query does not block a short one. There are four query kinds: `Q` plain, `P` profiled, `G`
paged, `N` counted.

## 5–6. The server routes it

A reader task hands each frame to its stream's own task. One fair writer drains every
stream's output queue in turn. Compilation and execution read the storage engine, so they
run on a blocking pool, never on the async reactor.

## 7. Compilation

`lex → parse → typecheck → flatten → reorder → Plan`.

| Phase | Does |
|---|---|
| lex / parse | A lossless tree with spans |
| lower | A typed tree the later phases run on |
| typecheck | Types, in side tables |
| flatten | Fold constants, collect constraints, hoist nested generators, decide what seeks and what filters |
| reorder | Choose the loop order |

<Demo kind="parse">{`N where F = code.File "src/lib.rs"; code.Decl {file = F, name = N, line = _}`}</Demo>

Two things to know. Constants and constraints are collected before the order is chosen, so
where you write them does not matter. And the reorderer moves a statement that reads a
variable a later statement binds, rather than refusing it.

The output is the contract between the two halves of the system:

```rust
struct Plan {
    nvars: usize,       // the size of the register file
    body: Box<[Step]>,  // ordered: [0] outermost … [n-1] innermost
    head: Project,      // how to build each output row
}
```

For our query:

```plan
  r0 <- codemarkup.SearchEntry scan
       where name == "Crc32"
  r1 <- codemarkup.SymbolXRef seek[target = r0.symbol, file = _, span = _]
  head {at = r1.span, f = r1.file}
```

Two nested loops. The outer one scans `SearchEntry` and filters on `name`, because the
key's leading field is open. The inner one seeks `SymbolXRef`, because its key leads with
`target` and the symbol is spliced in. That difference is most of what a query costs. See
[Query efficiency](query-efficiency.html).

## 8. The row descriptor, once

<Sequence>{`
← T  {f: src.File, l: int}
`}</Sequence>

A query's row shape comes from its head, so it is sent once per stream. Every row after it
is positional, with no field names on the wire.

## 9. The nested loop

The executor is one loop over a `depth` cursor:

```text
loop:
  if depth == body.len():          # past the innermost step — a full row is bound
      hand the row to the consumer
      on Continue: depth -= 1      # backtrack, look for the next row
      on Suspend:  depth -= 1; return Suspended{cursor}

  else match body[depth]:
      Level: open the next source if needed; pull the next matching row
             matched   → bind into registers; depth += 1
             drained   → next source, or back up a level
      Derive: compute the value once, descending; report exhausted, ascending
      Test:   probe each source for one row; pass (depth += 1) or drop the row
```

Three properties of that loop are invariants: a register holds the whole row and fields
decode lazily ([I5](invariants.html#i5)); values never enter the scan loop
([I6](invariants.html#i6)); it is a state machine, not recursion, so it can suspend to
bytes ([I7](invariants.html#i7)). [Executor & resume](executor.html) has the detail.

## 10. Encoding a row

The wire carries no field names, arities or types. Both peers hold the schema and the
descriptor, so a row is just its values, concatenated.

<Sequence>{`
← D  one row
← D  one row
…
`}</Sequence>

## 11. The chunk boundary is a real resume

Rows go out 256 at a time. At each boundary the executor suspends:

1. The loop state is serialised into a `Cursor`: one detached row per open level, and
   nothing else.
2. The snapshot is dropped ([I8](invariants.html#i8)).
3. A cancel gets its chance to land. `--limit`, `:cancel` and Ctrl-C all act here.

The next chunk resumes from those bytes and produces exactly what an uninterrupted run
would ([I4](invariants.html#i4)). The token carries a version and a plan fingerprint, so a
cursor from another plan is refused.

This is what makes paging stateless. A `G` query returns rows plus an `r` frame carrying
the token, and page two is a fresh request. Nothing lives in the server between pages.

## 12. The end of the stream

<Sequence>{`
← p  the profile, if the query was a P (once, just before the end)
← C  complete, with counts
`}</Sequence>

```text
STEP                    EXAMINED
codemarkup.SearchEntry  904       full scan
codemarkup.SymbolXRef   5
909 examined, 5 produced
```

The profile is per step of the plan. Read it against the plan: the plan is the intent,
this is the outcome.

## 13–15. The client renders

Rendering is always client-side. The server never produces JSON.

| Format | Streams? | Shape |
|---|---|---|
| `jsonl` | yes | One JSON value per line |
| `json` | yes | One document, written incrementally |
| `raw` | yes | Tab-separated fields |
| `table` | no | Aligned columns. Buffers, because widths are not known until the last row |
| `count` | n/a | The number only, from an `N` query |

### Expanding a reference

A row carries a reference as an id:

```json
{"to": "#4:1", "file": "#9:2", "at": {"line": 2, "col": 4, "length": 12}}
```

A query cannot name a fact by id, so the client asks the protocol:

<Sequence>{`
→ F  a batch of ids, per predicate
← f  one key each, positionally, or an absence
`}</Sequence>

The client walks it breadth-first, one round trip per level, one point read per distinct
id, cached across pages.

```json
{"to": {"module": {"file": "Boxops.Fjord.Client/Crc32.cs", "name": "Boxops.Fjord.Client"}, "name": "Crc32", "line": 7}, "file": "Boxops.Fjord.Client/Blocks.cs", "at": {"line": 98, "col": 24, "length": 5}}
```

The answer is the key, not the value: a reference names an identity, and it is the same
shape a producer wrote. If a fetch is refused, the rows still print with ids in them.

## How long it takes

On the reference box, compiling takes 4–14 µs. The executor's floor is about 330 ns per
row. Encoding a row costs about 1.5× the executor's work, and the wire above it another
3.6×. That is why `--count` exists: it runs the same plan and skips the part that costs.
See [Performance](performance.html).

## Where a write goes instead

<Sequence>{`
→ W  open a write stream
← G  ready for blocks
→ d  one block: [sync][magic][name][count][length][crc][facts]
→ d  and the next
→ c  done
← C  complete: facts written, facts deduped, id range per predicate
`}</Sequence>

Per block: decode, validate against the embedded schema, intern nested references
bottom-up, encode, write both maps atomically. See
[Wire protocol](wire-protocol.html#the-write-stream) and
[Storage](storage.html#interning-a-nested-fact).
