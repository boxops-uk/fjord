```bash
fjord shell <db>
```

Always over the wire, even against a server on the same machine. Syntax highlighting comes
from the compiler's own lexer. A line with an unclosed `{` or `(` continues on the next.

Commands are `:`-prefixed. The psql spellings (`\d`, `\l`, `\c`, `\timing`, `\more`) work
as aliases.

## Commands

```bash
fjord --data-dir ./db shell code
```

```text
fjord shell — `code` on ./db/fjord.sock
  28 predicate(s) · rows print as jsonl · :help for commands
```

|---|---|---|
| `<query>` | | Compile it locally, send it, print the rows |
| `:type <query>` | | The type of its head |
| `:plan <query>` | | The plan it compiles to, without running it |
| `:facts <predicate>` | | Every row of one predicate |
| `:schema [name]` | `\d`, `:d` | The served schema, or one predicate, or a prefix |
| `:more` | `\more`, `:m` | The next page of the last result |
| `:limit [n]` | | Rows per page |
| `:format <f>` | | `sigla`, `jsonl`, `json`, `raw` |
| `:id <id>` | | What a fact id names, written `code.Decl#1` |
| `:expand [hops]` | | Show the fact a reference names, not its id. Bare toggles it |
| `:cancel` | `\cancel` | Stop the last result early |
| `:timing` | `\timing` | Toggle how long a page took |
| `:profile` | `\profile` | Toggle rows examined per plan step |
| `:list` | `\l`, `:l` | The databases on this server |
| `:interning` | `\i`, `:i` | The write path's counters, per database |
| `:connect <db>` | `\c`, `:c` | Switch to another database |
| `:clear` | | Clear the screen |

### The shell compiles what you type

It holds the schema the server serves, so a mistake is a diagnostic with no round trip,
and `:plan` and `:type` answer without running anything. Where the two compilers could
disagree, the server decides what runs.

### Paging holds a real cursor

```text
sigla> :limit 3
  3 row(s) per page
sigla> F where src.File F
  : str
"Boxops.Fjord.Client/Blocks.cs"
"Boxops.Fjord.Client/Buffers.cs"
"Boxops.Fjord.Client/Crc32.cs"
  :more for the next 3 — 3 so far
sigla> :more
"Boxops.Fjord.Client/Errors.cs"
"Boxops.Fjord.Client/FjordAddress.cs"
"Boxops.Fjord.Client/FjordConnection.cs"
  :more for the next 3 — 6 so far
```

`:more` resumes from a token the server handed back. Nothing is held between pages. The
`: str` line is the row descriptor, the shape of the head.

### `:id` — what a fact id names

```text
sigla> {f = F} where code.Decl {file = F, name = "key_of", line = _}
{f = code.File#1}
  1 row(s)
sigla> :id code.File#1
"store/keys.py"
```

A query cannot name a fact by id, because ids change when a database is rebuilt. Asking at
a prompt, where the id is on the line above, is fine. A catalogue id is refused, because
those rows are positions in a listing.

### `:expand` — show the fact a reference names

```text
sigla> R where R = codemarkup.SymbolXRef _
  : codemarkup.SymbolXRef
"#9:225"

sigla> :expand
  references expand into the facts they name, all the way down
  each one is a point read — :timing counts them per page
sigla> R where R = codemarkup.SymbolXRef _
  : codemarkup.SymbolXRef
{"target": "scip-csharp-2 nuget Boxops.Fjord.Client 0.4.0.0 Boxops/Fjord/Client/Crc32#", "file": "Boxops.Fjord.Client/Blocks.cs", "span": {"start": 4808, "length": 5}}
```

One point read per distinct id, cached across pages. A reference that resolves to nothing
is reported, not hidden.

### `:profile` — rows examined

```text
sigla> :profile
  profile is on
  what the next query examines is reported when it ends
sigla> {f = F, at = S} where
         codemarkup.SearchEntry
           {nameLowercase = _, name = "Crc32", kind = _, symbol = T, file = _, line = _};
         codemarkup.SymbolXRef {target = T, file = F, span = S}
STEP                    EXAMINED
codemarkup.SearchEntry  904       full scan
codemarkup.SymbolXRef   5
909 examined, 5 produced
```

Per step of the plan. Read it against `:plan`: the plan is the intent, this is the
outcome. A `:limit` that cancels early reports no profile.

### `:schema` — and prefixes

```text
sigla> :schema codemarkup.SymbolXRef
  predicate codemarkup.SymbolXRef: { target: src.Symbol, file: src.File, span: { start: int, length: int } }
sigla> :schema codemarkup.
```

An exact name describes one predicate. Anything else is a prefix. Virtual predicates are
listed too: `:list` is a query over `fjord.db.List`, and `:interning` over
`fjord.db.Interning`.

## Things to try

The same question twice, once against a key that leads with the wrong field:

```sigla
:plan E where E = codemarkup.SearchEntry
                   {nameLowercase = _, name = "Crc32", kind = _, symbol = _, file = _, line = _}
:plan S where codemarkup.SymbolByName {name = "Crc32", symbol = S}
```

```text
  r0 <- codemarkup.SearchEntry scan
       where name == "Crc32"
  head r0#

  r0 <- codemarkup.SymbolByName seek[name = "Crc32", symbol = _]
  head r0.symbol
```

Run both with `:profile` on and compare the `EXAMINED` column.

Names nothing refers to:

```sigla
D.name where D = codemarkup.SearchEntry _; !codemarkup.SymbolXRef {target = D.symbol}
```

Reading through a reference, which adds a fetch level:

```sigla
{name = N, file = P} where
  codemarkup.SearchEntry {nameLowercase = "crc".., name = N, kind = _, symbol = _, file = F, line = _};
  F = src.File P
```

```text
  r0 <- codemarkup.SearchEntry seek[nameLowercase = "crc".., name = _, kind = _, symbol = _, file = _, line = _]
  r1 <- src.File fetch[r0.file]
  head {file = r1.0, name = r0.name}
```
