This tour indexes the repository's own .NET solution with its Roslyn-based indexer, then
asks it questions. It takes about ten minutes and assumes you have read
[Getting started](getting-started.html). Every output block is what the command printed.

Set up once. `FJ` is a Fjord checkout with `cargo build --release` done and the .NET SDK on
the path:

```bash
cd /tmp && mkdir fj-tour && cd fj-tour
FJ=/path/to/fjord
AP=$FJ/target/release/fjord
```

## 1. A schema you can read

```bash
$AP schema check $FJ/schemas/demo.sigla
```

```text
11 predicate(s) in 1 file(s)
  schemas/demo.sigla
fingerprint 0x03678fcd1e7924e3
```

The sample schema has one predicate per construct the language supports. The fingerprint
is computed over a canonical form, so two files that mean the same thing get the same
number.

```bash
$AP schema fingerprint $FJ/schemas/demo.sigla
```


`code.Kind` and `code.KindOf` hold the same data with the fields in opposite order. That is
the index design, and [step 6](#6-read-the-plan) shows why.

## 2. Create, and serve

The indexer writes `dotnet.sigla`, a sixty-five-predicate schema composed from five files.

```bash
$AP --data-dir ./db --schema-path $FJ/schemas create code --schema $FJ/schemas/dotnet.sigla
$AP --data-dir ./db serve --ready-file ./ready &
while [ ! -e ./ready ]; do sleep 0.1; done
```

```text
created code (01M1PCG31908ZED3YT1YKQBT9D) against /path/to/fjord/schemas/dotnet.sigla
fjord serve
  data dir   ./db
  socket     ./db/fjord.sock
  protocol   4
  connections 524288 at once  (half the descriptor limit; --max-connections sets it)
  databases  1
    code                 writable
```

A server has no schema of its own. Each database is served from the copy embedded at
create.

Read the two server counts together: **1.7 million facts touched, 158 thousand rows
created.** Every reference the indexer wrote carried its target as a whole nested fact
rather than an id:

```text
codemarkup.SymbolXRef {
  target = src.Symbol                                     ← a whole fact, not an id
    "scip-csharp-2 nuget Boxops.Fjord.Client 0.4.0.0
     Boxops/Fjord/Client/Crc32#",
  file = src.File "Boxops.Fjord.Client/Blocks.cs",        ← nested again
  span = { start = 4808, length = 5 }
}
```

The server writes each nested fact the first time and deduplicates it every time after.
That is why an indexer needs no map from entities to ids and no emission order: it emits
what it holds, where it stands in the syntax tree.

The 6,883 references "outside the index" point at the BCL and packages. Real code points
at code nobody walked, and the indexer says so rather than inventing targets.

## 4. First questions

```bash
$AP --data-dir ./db query code 'F where src.File F' --limit 3
```

```text
VALUE
Boxops.Fjord.Client/BlockTarget.cs
Boxops.Fjord.Client/Blocks.cs
Boxops.Fjord.Client/Boxops.Fjord.Client.csproj
3 row(s)
fjord: stopped at 3 rows; raise or drop --limit to see the rest
```

`--limit` cancels the stream after N rows. The query itself is unchanged.

A prefix on the leading key field is a range:

```bash
$AP --data-dir ./db query code \
  '{name = N, line = L} where codemarkup.SearchEntry
     {nameLowercase = "b".., name = N, kind = _, symbol = _, file = _, line = L}' --limit 5
```

```text
LINE  NAME
27    BadFacts
29    BadQuery
36    Bare
548   BaseOfKind
84    Batch
5 row(s)
fjord: stopped at 5 rows; raise or drop --limit to see the rest
```

The columns are alphabetical because a query's record fields are sorted by name. A
schema's fields are never sorted: their order is the key order.

## 5. A reference is an id, until you ask

```bash
$AP --data-dir ./db query code 'R where R = codemarkup.SymbolXRef _' --format jsonl --limit 2
```

```json
"#9:225"
"#9:227"
```

`#9:225` is predicate 9, sequence 225. A query cannot name a fact by its id, only by its
key, so expansion is the client's job:

```bash
$AP --data-dir ./db query code 'R where R = codemarkup.SymbolXRef _' \
  --format jsonl --limit 2 --expand
```

```json
{"target": "scip-csharp-2 nuget Boxops.Fjord.Client 0.4.0.0 Boxops/Fjord/Client/Crc32#", "file": "Boxops.Fjord.Client/Blocks.cs", "span": {"start": 4808, "length": 5}}
{"target": "scip-csharp-2 nuget Boxops.Fjord.Client 0.4.0.0 Boxops/Fjord/Client/Crc32#", "file": "Boxops.Fjord.Client/Blocks.cs", "span": {"start": 4834, "length": 5}}
```

The target is a string, a SCIP symbol, so a reference can name a declaration in another
database. An id would mean nothing outside the database that issued it.

## 6. Read the plan

The shell compiles locally, so `:plan` answers without running anything.

```bash
$AP --data-dir ./db shell code
```

```text
sigla> :plan {f = F, at = S} where
         codemarkup.SearchEntry
           {nameLowercase = _, name = "Crc32", kind = _, symbol = T, file = _, line = _};
         codemarkup.SymbolXRef {target = T, file = F, span = S}
  r0 <- codemarkup.SearchEntry scan
       where name == "Crc32"
  r1 <- codemarkup.SymbolXRef seek[target = r0.symbol, file = _, span = _]
  head {at = r1.span, f = r1.file}
```

`SearchEntry`'s key leads with `nameLowercase`, so a constraint on `name` cannot narrow the
scan. It only **filters**. `SymbolXRef`'s key leads with `target`, so the symbol **seeks**
straight to its references.

`--profile` shows what that cost:

```bash
$AP --data-dir ./db query code \
  '{f = F, at = S} where
     codemarkup.SearchEntry
       {nameLowercase = _, name = "Crc32", kind = _, symbol = T, file = _, line = _};
     codemarkup.SymbolXRef {target = T, file = F, span = S}' --profile
```

```text
AT         F
{4808, 5}  #56:2
{4834, 5}  #56:2
{4847, 5}  #56:2
{4860, 5}  #56:2
{4873, 5}  #56:2
5 row(s)
STEP                    EXAMINED
codemarkup.SearchEntry  1093      full scan
codemarkup.SymbolXRef   5
1098 examined, 5 produced
```

1,093 rows examined to find one. The fix is to ask by the leading field:

```text
sigla> :plan E where E = codemarkup.SearchEntry {nameLowercase = "crc"..}
  r0 <- codemarkup.SearchEntry seek[nameLowercase = "crc".., name = _, kind = _,
                                    symbol = _, file = _, line = _]
  head r0#
```

Now the prefix is a range, not a filter. [Query efficiency](query-efficiency.html) is the
full rule.

## 7. Paging holds a real cursor

```text
sigla> :limit 3
  3 row(s) per page
sigla> F where src.File F
  : str
"Boxops.Fjord.Client/BlockTarget.cs"
"Boxops.Fjord.Client/Blocks.cs"
"Boxops.Fjord.Client/Boxops.Fjord.Client.csproj"
  :more for the next 3 — 3 so far
sigla> :more
"Boxops.Fjord.Client/Buffers.cs"
"Boxops.Fjord.Client/Crc32.cs"
"Boxops.Fjord.Client/Errors.cs"
  :more for the next 3 — 6 so far
```

`:more` is not a re-run with an offset. The server suspended the query into a small token
and handed it over. Nothing is held between pages, so a web tier can page without holding
a connection.

## 9. Your own schema

```schema
# people.sigla
schema demo {

  # A scalar key: the whole key is one string.
  predicate Person : string

  # A record key. Field order is key order, so this is fast at
  # "who does this person know" and only filters the other way.
  predicate Knows : { from : Person, to : Person }

  # A value side (`-> T`) is fetched only when a query asks for it.
  predicate Age : { person : Person } -> int
}
```

```bash
$AP schema fingerprint people.sigla
```

```text
ID  PREDICATE    TYPE                                    FINGERPRINT
0   demo.Age     { person: demo.Person } -> int          a3b1b02ea361
1   demo.Knows   { from: demo.Person, to: demo.Person }  080f8e02ff95
2   demo.Person  string                                  34b7f70464c8
```

Adding a predicate is compatible. Changing one is not, including reordering its fields:

```bash
$AP schema diff people.sigla people2.sigla    # a fourth predicate added
$AP schema diff people.sigla people3.sigla    # `Knows` fields swapped
```

```text
Compatible (1 added)
  + demo.Employer

Breaking (1 predicate(s))
  ~ demo.Knows  (modified: 080f8e02ff957601 → c1779584fe40b587)
```

Create a database through the running server:

```bash
$AP create './db/fjord.sock//people' --schema people.sigla
```

```text
created people (01M0BN8AG2APYZB3B5YXGY58VW) against people.sigla
```

The address form is `[where//]name[@instance]`. See [Addressing](cli.html#addressing).

## What the tour showed

| You saw | The rule behind it |
|---|---|
| 1.7 M facts deduped against 158 K created | Nested references are deduplicated on write |
| A name that filtered and a symbol that seeked | Field order is the index design |
| `#9:225` in a row, expanded on request | A stored reference is an id; expansion is the client's job |
| `:more` returning the next three | A resume token is bytes, so paging holds nothing open |
| A caret with no round trip | The client compiles; the server decides what runs |
| `complete`, and a refused writer | Sealing is one way, and enforced at connection time |
